Кто ждёт ответа
от PostgreSQL?

Quill генерирует SQL в обеих сборках. В JDBC поток остаётся занят, пока синхронный вызов ждёт ответ. Vert.x регистрирует ожидание в event loop, а ZIO приостанавливает fiber. При большом числе запросов в полёте это меняет расход потоков приложения.

Два запроса, два соединения

В обеих схемах A и B отправлены по разным соединениям. Для примера ответ B приходит первым. Столбцы показывают порядок событий, без масштаба времени.

Заблокированный поток обычно не расходует CPU, пока спит в ожидании сокета. Он остаётся занят этим вызовом, сохраняет стек и не может взять другую задачу. HikariCP переиспользует соединения, а Quill переносит JDBC-вызовы на blocking executor ZIO. Поэтому HTTP event loop свободен в обеих сборках. Разница здесь в том, сколько рабочих потоков удерживает ожидание SQL.

Что делает event loop

Vert.x SQL Client работает с PostgreSQL по сетевому протоколу через неблокирующие каналы Netty. Event loop обслуживает несколько каналов. Когда от конкретного сокета пока нечего читать, он может обработать другой сокет, таймер или поставленную в очередь задачу.

  1. Запись. Клиент кодирует запрос и параметры, затем ставит данные на отправку. Если сокет временно не принимает всю запись, остаток ждёт готовности к записи.
  2. Готовность сокета. Транспорт ждёт готовности группы сокетов, например через epoll на Linux при использовании native transport Netty. Когда сокет доступен для чтения, цикл получает событие и запускает обработчик его канала. Один ответ может прийти несколькими порциями. Неполное сообщение остаётся в буфере до следующего чтения.
  3. Разбор протокола. Клиент собирает ответ из сообщений PostgreSQL, обрабатывает строки или ошибку и завершает Future операции.
  4. Продолжение. Callback передаёт результат в ZIO. Runtime планирует продолжение fiber, которая затем читает RowSet и строит объекты приложения.

Обработчики событий одного цикла выполняются последовательно. Если такой обработчик долго считает или ждёт синхронный I/O, остальные каналы этого цикла тоже ждут. В нашем SQL-пути callback завершения передаёт результат в ZIO. Преобразование строк в Scala-объекты находится в продолжении эффекта.

Для статической quotation Quill строит SQL при компиляции. Во время исполнения контекст получает соединение из Pool, кодирует значения из lift в Tuple и вызывает connection.preparedQuery(sql).execute(tuple). Vert.x возвращает Future. Адаптер fromFuture регистрирует обработчик завершения через ZIO.async.

Упрощённая схема моста. В реализации также обработаны синхронные исключения при создании Future и повторное завершение.

ZIO.async[Any, Throwable, A] { resume =>
  future.onComplete { result =>
    if (result.succeeded()) resume(ZIO.succeed(result.result()))
    else resume(ZIO.fail(result.cause()))
  }
}

Пока операция не готова, fiber приостановлена. Состояние продолжения хранится в ZIO, поэтому оно не привязано к стеку ожидающего потока. После callback ZIO продолжает её через свой runtime. В коде контекста следующий эффект извлекает строки, запускает декодеры Quill и возвращает List[A].

Зачем драйверу свой слой привязки SQL-параметров

Для PostgreSQL выражение $1 IS NOT NULL не даёт серверу достаточно информации о типе $1. Так обычные getOrElse, isEmpty и forall с lifted Option могли получить 42P18 при подготовке. Alpha.2 сохраняет тип NULL через кодек и передаёт его в SQL, например ($1)::text IS NOT NULL. Остальные скалярные сравнения сохраняют вывод типа по столбцу, что важно для enum.

Тот же слой задаёт типы decimal и массивов и различает json, jsonb, SQL NULL и значение JSON null. Он работает и для курсоров, где statement готовится до передачи tuple.

Где Vert.x может дать выигрыш

Преимущество проявляется, когда много операций одновременно ждут сеть или сервер. Например, при 400 SQL-операциях в секунду и среднем времени ожидания 20 мс в устойчивом режиме в среднем 8 операций находятся в ожидании. В синхронном JDBC-пути это около восьми занятых ожиданием потоков. В native-пути это восемь ожидающих операций, чьи сокеты обслуживает event loop. Это расчёт по закону Литтла на условных числах.

Пул соединений
Обе сборки ограничены 16 соединениями. В показанном режиме, без конвейеризации запросов на одном соединении, остальные операции ждут выдачи соединения. При насыщении пула именно очередь может определять p99.
Работа PostgreSQL
Индексы, блокировки, планы и объём данных определяют серверную стоимость запроса. Смена транспорта сама по себе не ускоряет этот участок.
Работа клиента
Разбор протокола, декодирование строк и выделение памяти по-прежнему требуют CPU. Большой результат способен упереться именно в эти расходы.

Транзакция удерживает одно соединение до commit или rollback. Quill хранит его для текущей операции в FiberRef. Обычный run собирает весь результат. При чтении через stream контекст запрашивает порции у курсора, по умолчанию по 128 строк, и держит соединение до закрытия потока.

Для сравнения на своём приложении стоит фиксировать SQL, данные, лимит пула и нагрузку. Измерять отдельно время получения соединения, время SQL, p95/p99 запроса, число рабочих потоков и CPU приложения. Функциональные проверки этой демки показывают совпадение поведения, а сравнение производительности потребует такого прогона.

Как это подключено в Conduit

HTTP, сервисы и QDSL компилируются из общих исходников. В JDBC-сборке Database предоставляет DataSource через HikariCP. В native-сборке он предоставляет Vert.x Pool, созданный на экземпляре Vert.x приложения. Репозиторий в обоих случаях вызывает database.execute(ctx.run(...)).
