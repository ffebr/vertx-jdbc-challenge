00 / ТЕЗИС

Меняется исполнитель,
а не язык запросов.

Quill quotation описывает выборку и преобразование данных. JDBC или native Vert.x определяют, каким способом SQL уйдёт в базу и как вернутся строки.

В Conduit общий код приложения компилируется в двух вариантах. Репозитории и сервисы общие; различается небольшая граница подключения: контекст, пул, кодеки, предоставление эффекта и перевод ошибок. Это позволяет сравнить два пути исполнения на одном API и одной схеме.

Native-реализация не является JDBC-драйвером и не эмулирует произвольные вызовы java.sql. Это исполнитель Quill на Vert.x SQL Client: quotations перекомпилируются, JDBC-зависимые кодеки адаптируются.

02 / QDSL

Запросы остаются
выразимыми в Scala.

В статических quotations SQL строится Quill при компиляции; динамически формируемые части могут вычисляться во время исполнения. lift передаёт значение через encoder как параметр, а не склеивает его с SQL-строкой.

МИНИ-ЭКСПЕРИМЕНТ

Что означает None?

Выберите вход и сравните концептуальные параметры. Это схема binding, не запрос к базе.

QDSL lift(None).getOrElse(column)
ПАРАМЕТРЫ $1 = NULL · $2 = NULL
ТИПЫ $1 = text · $2 = text
ИСХОДНАЯ ФОРМА CASE CASE WHEN $1 IS NOT NULL THEN $2 ELSE email END
ФОРМА С ТИПИЗИРОВАННЫМ NULL CASE WHEN ($1)::text IS NOT NULL THEN $2 ELSE email END

Ожидаемое значение email: текущее значение сохранится.

Схематичная иллюстрация параметров и SQL, не запрос к базе. Для optional update None сохраняет поле; это не команда очистки в SQL NULL.

03 / ВЫПОЛНЕНИЕ

Future возвращается
в ZIO fiber.

Vert.x SQL Client работает асинхронно: после отправки запроса ZIO fiber ожидает callback через ZIO.async, не удерживая поток на синхронном SQL-вызове. При завершении ошибки или результата fiber продолжается и выполняет декодирование.

СХЕМА 02 · Асинхронный ввод-вывод освобождает поток ожидания; вычисления CPU остаются.

Асинхронность не означает «бесплатно»

Драйвер не выполняет native SQL через attemptBlocking: получение соединения, запросы и cursor идут через callbacks. Но сериализация, подготовка Tuple, декодирование и JSON занимают CPU.

Отдельный пример — bcrypt cost 10 через at.favre.lib:bcrypt:0.10.2. Его синхронные hash/verify обёрнуты в ZIO.attemptBlocking при регистрации, входе и смене пароля. Это защищает обычный executor от долгой операции, но не делает вычисление дешевле и не ограничивает конкуренцию. Отдельного ограниченного CPU executor пока нет. Обычный авторизованный запрос проверяет JWT и не пересчитывает bcrypt.

JDBC по-прежнему имеет синхронный контракт: Hikari управляет соединениями, а не превращает ожидание JDBC в async API. Здесь нет измерений, доказывающих преимущество по скорости.

04 / ТИПЫ SQL

NULL должен
иметь тип.

PostgreSQL разбирает не только текст SQL, но и тип каждого параметра. В условии CASE WHEN $1 IS NOT NULL THEN $2 ELSE email END сервер не всегда может вывести тип $1. В native prepare это приводило к 42P18: indeterminate datatype для optional update, isEmpty и forall.

БЕЗ ИНФОРМАЦИИ О ТИПЕ CASE WHEN $1 IS NOT NULL THEN $2 ELSE email END Параметр-проверка не связан со столбцом
ТИПИЗИРОВАННЫЙ NULL CASE WHEN ($1)::text IS NOT NULL THEN $2 ELSE email END Смысл CASE прежний; тип известен серверу

В alpha.2 кодек сохраняет тип SQL NULL, включая Option и MappedEncoding. PostgreSQL binding-слой добавляет cast там, где тип нельзя вывести. Decimal получает numeric; массивы сохраняют array type; JSON и JSONB передаются как JSON-текст с приведением к типу столбца.

Скалярные сравнения не приводятся огульно к text: это могло бы сломать сравнение с PostgreSQL enum. JSON null, SQL NULL и строка JSON "null" остаются разными значениями. Тексты параметров сканируются с учётом кавычек, комментариев и dollar-quoted блоков.

05 / ВРЕМЯ ЖИЗНИ

Соединение принадлежит
scope и fiber.

В native-транзакции контекст заимствует соединение, начинает транзакцию и кладёт его в FiberRef. Вложенные ctx.run используют ту же связь. Успех приводит к commit, ошибка или interruption — к rollback и освобождению соединения.

01 / ОТКРЫТЬ

Scoped acquire получает connection из Pool.

02 / ПЕРЕДАТЬ

FiberRef даёт вложенным действиям текущую транзакцию.

03 / ЗАВЕРШИТЬ

Commit или rollback; затем release при любом выходе.

Вложенный ctx.transaction переиспользует транзакцию и не создаёт savepoint. Отдельный трудный случай — interruption до callback acquire: соединение может прийти уже после отмены fiber. Runtime регистрирует владение в scope и закрывает позднее полученный ресурс.

Поток и отмена

ctx.stream использует cursor с настраиваемым fetch size (по умолчанию 128); следующее чтение запрашивается по мере потребления ZStream. Если потребитель соберёт весь поток в коллекцию, его память всё равно растёт. При interruption PostgreSQL-путь отправляет cancelRequest, но сервер мог уже выполнить побочные эффекты. MySQL/MariaDB и DB2 прерывают соответствующее соединение.

06 / МИГРАЦИЯ

Начинать с границы
подключения.

Практический перенос не требует сначала переписывать сервисы. Нужны отдельные сборки или точка компиляции, где выбираются контекст и зависимости; общий адаптер Database выдаёт репозиториям Task[A] и переводит ошибки persistence в ошибки приложения.

01 Зафиксировать JDBC-поведение интеграционными тестами.
02 Выделить фабрику контекста, пула, окружения и маппинга ошибок.
03 Подключить Vert.x Pool и перекомпилировать quotations.
04 Перенести кодеки, использующие setObject, getObject или vendor unwrap.
05 Сравнить те же сценарии, включая None/Some, rollback, stream и interruption.
06 Измерить нагрузку и настроить таймауты, пул и эксплуатационные метрики.
Минимальная зависимость и consumer-проверка

  jdbc/test native/test jdbc/stage native/stage

GitHub Packages требует учётные данные с доступом к registry. Не добавляйте секреты в build-файл или репозиторий. Published consumer workflow проверяет именно скачанные артефакты.

Кодеки Quill, привязанные к JDBC API, придётся адаптировать к native Tuple и Row. При этом логические MappedEncoding, например UserId ↔ Long, могут остаться применимыми при наличии scalar-кодека.

В демонстрации есть маленькие PostgreSQL infix для nextval(...) и now(): перенос QDSL не переносит автоматически SQL-семантику на любую СУБД.

07 / ИНЖЕНЕРНЫЙ ВЫВОД

Что команда
получает — и что нет.

Рефакторинг читаемости тоже влияет на поддержку: прежде результат сводного запроса собирался в семиэлементный tuple. Теперь форма результата названа типом, а валидация обязательных полей вынесена в общие helpers сервиса. Это делает структуру результата видимой при чтении кода и снижает шанс перепутать соседние поля.

Сильные свойства

  • Общий QDSL компилируется для двух исполнителей.
  • Native SQL имеет асинхронный сетевой контракт Vert.x.
  • DB lifecycle и ошибка SQL локализованы в адаптере.
  • Проверены типизированные NULL, streaming и транзакционный scope.

Требует решения

  • Bcrypt требует контроля параллелизма.
  • Нет savepoint-семантики вложенных транзакций.
  • Отмена запроса не гарантирует undo побочного эффекта.
  • Пулы с одинаковым max требуют отдельных tuning-решений.

Это архитектурная демонстрация и alpha/pilot публикация. Её вывод — миграция может быть локализована, если запросы уже выражены Quill DSL и прикладные кодеки отделимы от JDBC. Это не утверждение о полной drop-in совместимости с закрытым приложением или любым JDBC-кодом.

09 / ЧЕСТНЫЕ ГРАНИЦЫ

Поддержка — это
конкретный список.

Проверены PostgreSQL, MySQL, MariaDB и DB2. Oracle и SQL Server не входят в заявленную матрицу. Для MySQL/MariaDB returning ограничен одним автоматически сгенерированным ключом; одинаковые SQL-возможности всех серверов не обещаются.

Опубликованная версия — 0.1.0-alpha.2, доступ к GitHub Packages требует аутентификации. Это пилот, пригодный для оценки и контролируемого внедрения, а не готовая замена любого JDBC-драйвера.

Следующие вопросы для production-пилота

Проверить свои quotations и кодеки; задать лимиты bcrypt; согласовать таймауты и pool sizing; измерить latency и throughput под реалистичной конкуренцией; проверить rollback, отмену и частичные эффекты. Никаких выводов о скорости без такого бенчмарка здесь нет.

Разделить описание запроса и его исполнение — небольшой архитектурный шов. Ценность шва определяется не обещанием «асинхронности», а тем, насколько много поведения остаётся общим и насколько тщательно проверена граница.
